# Flint desktop implementation guide

Target: Chromium `158.0.8127.36`, using the ungoogled-chromium patch stack. The inspected base checkout was `cee9927bc2290e29109dcb9343b687e8608ece8c`. Windows x64 is the first installer target. macOS and Linux packaging follow after the shared WebUI and network behavior pass. This is a design and starter patch set. The patch contexts were checked on selected pinned files; no complete browser or installer was built. Paths below are relative to Chromium `src/` unless explicitly labeled “fork.” Work on a development branch. The scheme seed is intentionally separate from the independently usable patches.

## Phase 1 — Build configuration and per-user installation

1. In the fork, use `chromium_version.txt` and `downloads.ini` to acquire the matching source. Use the release's platform packaging workflow to prepare dependencies, prune binaries, apply `patches/series` and perform domain substitution. Place Flint diffs under fork `patches/flint/` and append their relative names to fork `patches/series` after the patches they extend. The credits edit requires upstream `extra/ungoogled-chromium/add-credits.patch`. A vanilla Chromium checkout alone lacks that edit.
2. Seed `out/Flint/args.gn` with the fork's `flags.gn` and required Windows packaging arguments. Merge the following settings by key. Keep the upstream empty OAuth credentials, disabled reporting and field-trial settings. Turning off reporting or removing keys does not remove account UI or every network client.
   
   ```gn
   is_chrome_branded = false
   is_debug = false
   is_component_build = false
   target_cpu = "x64"
   ```

   From the prepared source root in a Chromium build shell:

   ```powershell
   gn gen out/Flint --fail-on-unused-args
   autoninja -C out/Flint chrome mini_installer
   ```

   The target and executable may retain developer-facing names. Inspect the actual build arguments with `gn args out/Flint --list --short`. Reuse the pinned Windows toolchain requirements. The compile machine and the standard-user installation target have different prerequisites.

3. Apply `01-user-install.patch` to `chrome/install_static/chromium_install_modes.h`. It opts the build out of system-level installs. The existing check in `chrome/installer/setup/setup_main.cc` rejects an incompatible install mode. Launch the per-user installer from an ordinary account. A product rename alone does not isolate install state.
4. Before distributing, assign `kProductPathName`, `base_app_name`, `base_app_id`, the HTML/PDF ProgIDs and descriptions in `chrome/install_static/chromium_install_modes.h` to Flint-owned identities. Audit every COM and registration identifier in that same structure and allocate distinct persistent IDs for those Flint actually registers. Reserve the internal WebUI scheme for the browser; use a separate identifier if an OS launch protocol is necessary. Preserve explicit organization policy and OS application-control decisions. Expected Windows paths include `%LOCALAPPDATA%\Flint\Application` and a separate Flint user-data directory. Install, update, uninstall and reinstall beside Chromium under a standard account; check shortcuts, taskbar grouping, file associations, profile isolation and elevation prompts.
5. Package macOS for copying to `~/Applications/Flint.app` and Linux for extraction into a user-owned application directory with a user-local desktop entry. Verify sandbox operation on every supported Linux distribution. Installer tests must fail when sandbox prerequisites cannot be satisfied. Keep signed update verification even when distributing updates as offline files.

## Phase 2 — Product identity, internal URLs and credits

**Product text and icons.** Apply `02-brand-and-credits.patch`. It edits product fields in `chrome/app/theme/chromium/BRANDING`, standalone product/menu/helper strings in `chrome/app/chromium_strings.grd`, and the credited-project banner in `components/webui/about/resources/about_credits_reciprocal.tmpl`. The banner links Flint and identifies ungoogled-chromium as its base. Keep the license list generated by `tools/licenses/licenses.py` and upstream's `third_party/ungoogled-chromium/LICENSE`. Product-language changes must preserve authorship and license notices.

Finish visible sentence-level strings and translations separately; GRIT messages can change translation fingerprints. Audit welcome, downloads, error pages, accessibility labels, task manager, uninstall dialogs and all shipped locales. In `chrome/app/theme/chromium/BRANDING` choose a distinct macOS bundle identifier and the publisher's real signing identity before packaging. Replace `chrome/app/theme/chromium/win/chromium.ico`, `chrome/app/theme/chromium/mac/app.icns`, and the product-logo PNG families, including `chrome/app/theme/chromium/product_logo_48.png`. Use one approved Flint master mark, preserve all pixel sizes and ICO/ICNS representations, and supply monochrome/template variants where required. No Flint logo asset was supplied. Generate an exact asset manifest from the checkout, including platform installer resources, before replacing anything:

```powershell
rg --files chrome/app chrome/installer | rg -i '(chromium|product_logo|app_icon|document_icon).*(ico|icns|png|svg|bmp)$'
rg -n 'Chromium|Google Chrome' chrome/app/chromium_strings.grd chrome/app/theme/chromium chrome/installer
```

**Scheme migration.** A canonical `flint://` affects the origin of every trusted WebUI document. Treat this as its own migration branch. The included `02-scheme-migration-seed.patch` changes the canonical trusted scheme in `content/public/common/url_constants.h` and URL constants in `chrome/common/webui_url_constants.h`. **The seed alone is insufficient to ship or enable.** A settings page may navigate successfully while its JavaScript imports still point at the old origin.

- Inventory every literal, including generated-resource inputs and tests. The pinned `chrome/browser/resources/settings/route.ts` imports from `chrome://resources`; `chrome/browser/resources/settings/settings_main/settings_main.css` and `chrome/browser/resources/new_tab_page/app.css` also use that origin in CSS wrapper metadata. Move trusted imports and their build-time resolver rules together. Rerun this audit on each rebase. Keep extension APIs, external websites, untrusted WebUI and DevTools in their own trust domains.
- Follow dispatch through `chrome/browser/browser_about_handler.cc` and `chrome/browser/chrome_content_browser_client.cc`. Check URL parsing, browser-initiated navigation, resource serving, CSP generation, renderer process locks, and browser-interface binding for each affected host. Preserve upstream host-specific controllers and initiator checks. Never grant arbitrary sites, custom schemes or OS protocol launches WebUI access.
- Inspect `components/omnibox/browser/autocomplete_input.cc` for typed-URL classification and `chrome/browser/ui/toolbar/chrome_location_bar_model_delegate.cc` for display. The committed URL, address bar, copied URL and history must agree. Migrate legacy bookmarks via a versioned, idempotent profile migration for known internal destinations. Test bookmarks with fragments, encoded paths and query strings.
- Acceptance: open settings, credits, downloads, history, extensions and the WebUI index; check links, reload/back, search, assets, address-bar copy and bookmark restore. From an ordinary webpage verify that embedding a trusted WebUI or requesting its privileged interfaces is denied, and that untrusted WebUI is still isolated. Keep the migration branch out of release builds until these browser tests pass.

```powershell
rg -l 'chrome://|kChromeUIScheme' chrome components content ui services tools > flint-scheme-inventory.txt
```

## Phase 3 — User control, Group Policy and MDM

For personal devices, implement the hardening choices as registered defaults with ordinary user preferences. Mandatory browser policies and OS-enforced restrictions remain authoritative on managed devices. This guide does not include an implementation that bypasses school or workplace controls.

Use the effective preference and its control metadata in the settings UI. A recommendation can supply an initial value while permitting an override. A mandatory value displays its effective state and a management explanation. Enforce this at the write boundary as well as in the UI. In particular, `chrome/browser/extensions/api/settings_private/prefs_util.cc` already handles permitted settings and special cases for secure DNS. Route changes through that existing implementation when possible.

Illustrative C++ for a **registered Boolean preference only**, in a proposed new `chrome/browser/ui/webui/settings/flint_hardening_handler.cc`:

```cpp
bool SetUserBoolean(PrefService& prefs, const char* registered_key, bool value) {
  const auto* pref = prefs.FindPreference(registered_key);
  if (!pref || pref->GetType() != base::Value::Type::BOOLEAN ||
      !pref->IsUserModifiable())
    return false;
  prefs.SetBoolean(registered_key, value);
  return true;
}
```

Map a fixed set of typed actions to keys on the browser side. Never accept arbitrary pref names from JavaScript. Read the effective value after each change. Test Windows mandatory and recommended settings, macOS managed preferences, and Linux managed/recommended policies alongside clean unmanaged profiles. Deliver a policy change while the panel is open and verify the UI and active network configuration update together.

## Phase 4 — Account-free settings, network controls and obsidian theme

**Replace the account surface.** In `chrome/browser/resources/settings/route.ts`, split local profile management/import from account, Google services, sign-out and sync routes. Update the default-route selection, deep links, and every reference to a retired route in the same change. Replace the People entry in `chrome/browser/resources/settings/settings_menu/settings_menu.html` and People view in `chrome/browser/resources/settings/settings_main/settings_main.html` with a local profile view. Keep local bookmark/password import and profile switching. In `chrome/browser/ui/webui/settings/settings_ui.cc`, inventory the actual handlers registered for the target platform and remove account-only registrations. Follow reachable sign-in and sync service factories outside settings; retire account promos, startup initialization and sign-in entry points. The fork's `disable-gaia.patch` touches `google_apis/gaia/gaia_auth_fetcher.cc`; that patch alone does not establish complete removal. Verify clean profiles, upgraded profiles, avatar menus, first run, settings search and retired deep links. Preserve existing local profile data during upgrades.

**Add the panel.** Define a privacy child route in `chrome/browser/resources/settings/route.ts` and its typed property in `chrome/browser/resources/settings/router.ts`. Add a link row to `chrome/browser/resources/settings/privacy_page/privacy_page.html`. Proposed new files are `chrome/browser/resources/settings/privacy_page/flint_hardening_page.ts` and `chrome/browser/resources/settings/privacy_page/flint_hardening_page.html`. Wire them into `chrome/browser/resources/settings/BUILD.gn` and the privacy page's existing subpage loader. Localize the title “Privacy and Network Hardening,” descriptions, error text and search terms. Use existing settings controls for profile prefs, and a narrowly scoped browser handler for multi-pref transitions. Show whether changes apply to one profile or the entire browser.

| Control | Backend contract and acceptance condition |
|---|---|
| PAC and WPAD | Treat explicit PAC scripts and automatic discovery as separate sources. A file-extension filter misses PAC URLs without a suffix and local files. On unmanaged systems, reject PAC evaluation and automatic discovery before fetching or DNS/DHCP discovery. Retain explicit fixed proxies. If the effective configuration requires an unavailable PAC, surface a configuration error and fail closed. Verify zero discovery requests and zero silent direct-route fallback. |
| Strict DoH | Reuse the mode/template preferences exposed in `chrome/browser/extensions/api/settings_private/prefs_util.cc`. The inherited default in `chrome/browser/net/default_dns_over_https_config_source.cc` is **off**. Present local preset metadata and a custom HTTPS template validated by Chromium's DNS parser. Apply valid templates before selecting secure mode and handle partial failures. Test resolver outages, bootstrap DNS, VPN/split DNS and multiple profiles. A remote resolver receives queries; include a user-provided local HTTPS resolver option. |
| ECH and TLS | Report configured and negotiated states separately. ECH depends on usable DNS HTTPS records and server support. Keep certificate verification intact. Label a TLS 1.3 minimum explicitly and report incompatibility with older servers. Verify handshakes against controlled supporting and non-supporting endpoints. IP addresses and traffic timing remain observable. |
| WebRTC | Reuse the upstream default registered in `chrome/browser/ui/browser_ui_prefs.cc` for disabling non-proxied UDP. Expose effective mode and describe the effect on calls. Test ICE candidates and actual connections across direct, proxy, VPN and TURN configurations. The default alone is insufficient to promise IP anonymity. |
| Fingerprinting | Start with the two existing canvas/geometry patches listed in fork `patches/series`. Document exactly which outputs each alters and whether a restart is required. Prefer a small common preset; test consistency across frames, accessibility tools, canvas editors and repeated visits. |
| Cookies and storage | Use the typed cookie-controls preference already exposed in `chrome/browser/extensions/api/settings_private/prefs_util.cc`. Default new profiles to blocking third-party cookies. Keep partitioned storage semantics separate; verify cross-site iframe cookies, IndexedDB, cache and service workers with two top-level sites. Describe existing exceptions and private-window behavior. |
| Telemetry and pings | Preserve inherited removal of crash uploads, update pings and reporting. Display compiled-out features as disabled by build. For optional traffic the user can change, enumerate the consumers and verify each with process-level connection and DNS captures. Test a fresh profile, restart, idle, error reporting and a normal visit to a controlled website. |

**Network implementation boundaries.** Stage new preference declarations in proposed `chrome/browser/net/flint_hardening_prefs.h` and `chrome/browser/net/flint_hardening_prefs.cc`; register them from `chrome/browser/prefs/browser_prefs.cc`. For PAC changes, use the effective configuration consumed by `net/proxy_resolution/configured_proxy_resolution_service.cc`; platform discovery may also run before it reaches that service. Trace outbound discovery on each OS before declaring it covered. Inspect network-context construction in `chrome/browser/net/profile_network_context_service.cc` and TLS configuration in `services/network/ssl_config_service_mojo.cc`. A saved pref needs an observer or an explicit restart requirement. Add readers before adding UI toggles. Per-profile UI must never silently change a process-wide setting for other profiles.

**Theme.** Apply `04-obsidian-base.patch`. It sets native frame, toolbar, text and separator recipes in `chrome/browser/ui/color/chrome_color_mixer.cc`, and base host colors in the NTP and settings CSS files listed in Phase 2. Tab backgrounds and text take several recipes from toolbar/frame colors in `chrome/browser/ui/color/tab_strip_color_mixer.cc`. Extend this palette to selected, inactive, hover and keyboard-focus states, and to WebUI component tokens for cards, dialogs, menus, text fields and icons. A host background cannot recolor every nested component. Test clean profiles under both OS appearances, active/inactive windows, Incognito, forced colors and custom themes. Keep forced colors and focus outlines available. Capture settings, credits, new tab, downloads, extension management and first-run UI before packaging.

### Verification and release boundary

Apply each eligible diff with `git apply --check` from the **prepared Chromium source root**, then apply it. In a maintained fork, let its patch-series tooling apply the same diffs exactly once. Keep the scheme seed on the migration branch until its dependent changes land. Re-run GN generation, build the browser, installer and relevant test targets, and test on a clean non-admin account. Release only after checking coexistence, account removal, policy precedence, network behavior, accessible theme contrast and internal-origin isolation. The existing NoseyGames feature-pack ZIP is an extension/native-host distribution and requires separate integration if bundled with Flint.
